# 架构与设计取舍

## 分层

```
宿主层    src/core/host-bridge.ts · src/client/
          微信 PC 客户端 / 企业微信 / Electron 壳
          提供宿主能力（通知、角标、原生发送），并投递消息
              ↓  HostTransport.inject()
协议层    src/core/types.ts · src/protocols/
          各家微信协议 → NormalizedMessage
              ↓
核心层    src/core/     引擎骨架：事件总线、存储、配置、插件、分词
              ↓
领域层    src/analytics · src/guard · src/ai · src/manage
          纯业务逻辑，不感知协议，不依赖 HTTP
              ↓
装配层    src/runtime/  引擎运行时与 bootstrap
              ↓
接口层    src/api · src/client/panel.ts · src/cli.ts · src/plugins
```

依赖方向单向向下。领域层可以单独 `import` 使用（例如只把 `AnalyticsEngine` 接进自己的服务），
不必启动整个引擎。

### 为什么把宿主也当成一层

微信 PC 客户端插件与「引擎 + HTTP 中间件」的差别只有一处：**引擎被宿主反向调用**。
需要弹客户端通知、设置角标、弹保存框时，是引擎调宿主，方向与收消息相反。

把这种反向调用直接写成 `import` 宿主 API 会带来两个问题：领域层反向依赖宿主实现，
离线跑不起来；宿主版本差异（不同微信版本的 API 不同）会渗透进领域代码。

因此定义一份**能力契约** `HostBridge`：引擎按能力名调用，宿主按能力名注册，缺能力就降级。
目前覆盖 13 项能力（`notify`/`setBadge`/`setTitleBadge`/`openPanel`/`toast`/
`openExternal`/`pickFile`/`exportFile`/`readClipboard`/`writeClipboard`/`contacts`/
`nativeSend`/`shutdown`），新增能力只加枚举 + 类型，不动调用点。

判断能力是否可用靠「**是不是函数**」而不是「字段是否存在」：插件壳常见做法是
声明一堆可选方法却只实现一部分，用字段存在性判断会把空实现误判为可用能力。

## 关键设计决策

### 1. 消息入口只有一条，三种注入路径共用

PC 客户端进程内直投、本地 IPC、HTTP 中间件、离线导入——四条来源最终都调用
`Engine.ingestRaw()`（或它的上层 `HostTransport.inject()`）。

这条约束的价值在于**统计口径唯一**：如果「实时消息」与「导入消息」各走一套归一化，
同一个群会算出两套数字，而且这种偏差只在数据混用时才暴露，极难排查。

同理，`HostTransport` 的绑定用 getter 而不是字段持有适配器实例：
适配器由引擎的注册表工厂创建，工厂可能被多次调用；如果宿主入口持有的是另一个实例，
注入会落到一个没有订阅者的 transport 上——**消息全丢，日志却一切正常**。
这类「静默失败」是客户端插件最典型的坑，所以从结构上排除。

### 2. 协议差异收敛在适配器，归一化只做一次

各协议字段命名完全不同（`msgId`/`MsgId`/`newMsgId`、`fromUser`/`sender`），
但**归一化逻辑只有一份**：适配器负责「取字段」，引擎负责「转换」。因此：

- 新增协议 = 写一个 `ProtocolAdapter` + 配 `mapping`，零改动核心代码
- 时间戳统一毫秒、消息类型统一枚举，下游不必各自兜底
- 去重 ID 在归一化阶段定型，协议重投不会重复入库

### 2. 统计走预聚合，不扫全表

`messages` 表只做原始留存；报表全部读 `activity_buckets`（会话 × 时间桶 × 成员 × 类型）
与 `word_stats`。理由：报表是高频只读操作，全表扫描会随历史线性劣化，
而预聚合让查询成本只与**时间跨度**相关。

实测 10 万条消息的分组排行查询约 20ms。

### 3. 统计口径只在一处实现

「消息数」「成员数」「活跃度」这些口径只由 `Store.insertMessage` 的事务维护。
报表、风控、面板读的是同一份数据，不会出现「报表说 100 条，统计指令说 98 条」。

### 4. 风控是「规则（纯函数）+ 引擎（窗口与计分）」

规则签名 `(消息, 配置, 历史窗口) → 判定`，纯函数带来：

- 可单测：`test/guard.test.ts` 逐个规则钉住边界行为
- 可复现：误报能拿同样的输入重放
- 可热插拔：`createRules()` 按配置组装，自定义词表规则不需要写代码

**默认不自动处罚**。群聊里一次错误禁言会让群主失去信任，而漏报只是晚一步发现。
自动动作需要显式开启 `autoActions`，且只实现「发提醒」这一可撤销的动作。

### 5. AI 分层：网关 / 检索 / 摘要互相独立

- `LlmGateway` 只管 OpenAI 兼容协议、超时、并发闸门。换厂商改配置即可
- `Retriever` 不上向量库：群聊检索多是「人名/关键词/具体事项」，词法匹配召回足够，
  用 BM25 变体 + 时效衰减重排，零额外成本
- `Summarizer` 用「分段摘要 + 归并」处理长记录，单次请求上下文可控

**AI 关闭时功能不消失**：`summarize()` 退化为统计口径摘要（谁发言最多、类型分布），
仍是有用的信息。只有「群内问答」无降级路径，明确返回 503。

### 6. 插件按声明订阅，卸载不留悬挂监听

`Plugin.subscriptions()` 返回「事件 → 处理函数」，引擎用 `插件名:事件名` 作为订阅 key。
卸载时 `offAll(插件名)` 一次摘净。长跑进程里这类泄漏会让内存只增不减且极难定位。

插件依赖用 Kahn 拓扑排序，有环或依赖缺失直接启动失败。

### 7. 定时任务收在一层，业务只提供「跑什么」

`Scheduler`（`src/runtime/scheduler.ts`）是唯一接触 cron 的地方：插件只说
「这个表达式、这个动作」，换调度器（甚至换成 K8s CronJob）不动业务代码。

三条容易踩的坑在这一层挡掉：非法表达式**跳过并告警**而不是让进程起不来；
上一次未跑完时**跳过本次触发**（日报叠加推送在群里是可见事故）；
定时器全部 `unref()`，CLI 与 CI 不会因为后台 cron 挂住。

日报本身是纯函数 `buildDigest(store, conversationId, window)`：渲染逻辑可单测，
调度只做「取窗口 → 逐个群渲染 → 发送并记账」。定时任务的失败最难被发现，
所以状态（执行次数、失败次数、耗时、最后错误）被记账并在 `doctor` 与面板里可见。

### 8. 事件派发同步且互相隔离

`EventBus.emit` 同步调用各订阅者，单个订阅者抛错被捕获并转发到 `engine.error`，
不影响其他订阅者 —— 一个统计插件写库失败不该让风控插件漏掉这条消息。

同步派发保证了同一消息在所有订阅者眼中顺序一致。慢操作（LLM 调用、HTTP 请求）
由插件自己 `void (async () => ...)()` 排队，不阻塞链路。

### 9. 中文分词用 2-gram 而非词典

不引 jieba/segment：群聊统计要的是「高频词与话题倾向」，不是精确分词。
词典分词会带来几 MB 词典、原生依赖，且对梗、缩写、新词反而不如字级 n-gram 稳。
CJK 切 2-gram + 拉丁按词，零依赖且口径稳定。

## 数据模型

```
conversations  会话档案（累计消息数是历史口径，不随留存裁剪回退）
members        成员台账（会话 × 成员）
messages       原始消息（可裁剪）
activity_buckets  预聚合：会话 × 时间桶 × 成员 × 类型
word_stats     词频：会话 × 词（按「出现该词的消息数」计数）
events         风控与 AI 结论留痕
kv             群知识与内部状态
```

索引：`idx_messages_conv_ts`、`idx_messages_conv_sender_ts`、`idx_activity_conv_bucket`、
`idx_word_conv_count`、`idx_events_conv_ts`。

## 可注入点与降级

| 事实 | 处理方式 |
|---|---|
| 微信 PC 端是闭源客户端，无官方插件 SDK | 支持三条注入路径（进程内壳 / 本地 IPC / 导入），核心代码零改动 |
| 宿主 API 集合不可控 | 13 项能力全部可选，缺失时降级而非抛错 |
| 宿主回调里抛错会打断客户端消息循环 | `HostGateway` 三层隔离：缺失返回失败、抛错记账、通知按 key 限流 |
| 客户端 WebView 可能没有外网 | 面板压成单文件，CSS/JS/Logo 全内联 |
| 客户端 WebView 内核版本不可控 | 面板只用手写 ES5 兼容语法，不引框架、不引 polyfill |
| 畸形消息不应让插件崩掉 | `inject()` 返回结构化结果（`accepted` / `reason`），不抛错 |
| 插件可能热重载 | 替换宿主桥时清空通知去重窗口，避免新会话告警被旧窗口静默吞掉 |
| 「消息全丢」与「消息没来」在界面上无法区分 | 提供 `GET /api/health/deep`：用一条**不落库**的探针走完注入链路并给出结论 |
| 同一个进程里可能同时有客户端宿主与导入用的宿主 | 适配器按**选项指纹**决定复用还是另造，避免导入数据按实时 mapping 解析 |

## 已知边界

- **单机限定**：SQLite + 进程内窗口，未做多实例共享。要横向扩展需把 `Store` 与
  `GuardEngine` 的窗口换成 Redis/Postgres，接口已抽出。
- **群知识抽取是启发式的**：用「消息够长 + 含规则类词 + 非疑问句」筛候选，
  不逐条调 LLM（成本与稳定性都不划算）。候选与正式条目分表存，人工确认后才进问答语料。
- **语义审核未默认开启**：`guard.useAi` 需要 AI 可用；当前内置规则是词法+行为特征，
  覆盖不了纯语义的阴阳怪气与隐喻导流，需要时可扩展。
