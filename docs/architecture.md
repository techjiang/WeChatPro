# 架构与设计取舍

## 分层

```
协议层    src/core/types.ts · src/protocols.ts
          各家微信协议 → NormalizedMessage
              ↓
核心层    src/core/     引擎骨架：事件总线、存储、配置、插件、分词
              ↓
领域层    src/analytics · src/guard · src/ai · src/manage
          纯业务逻辑，不感知协议，不依赖 HTTP
              ↓
装配层    src/runtime/  引擎运行时与 bootstrap
              ↓
接口层    src/api · src/cli.ts · src/plugins
```

依赖方向单向向下。领域层可以单独 `import` 使用（例如只把 `AnalyticsEngine` 接进自己的服务），
不必启动整个引擎。

## 关键设计决策

### 1. 协议差异收敛在适配器，归一化只做一次

各协议字段命名完全不同（`msgId`/`MsgId`/`newMsgId`、`fromUser`/`sender`），
但**归一化逻辑只有一份**：适配器负责「取字段」，引擎负责「转换」。因此：

- 新增协议 = 写一个 `ProtocolAdapter` + 配 `mapping`，零改动核心代码
- 时间戳统一毫秒、消息类型统一枚举，下游不必各自兜底
- 去重 ID 在归一化阶段定型，协议重投不会重复入库

### 2. 统计走预聚合，不扫全表

`messages` 表只做原始留存；报表全部读 `activity_buckets`（会话 × 时间桶 × 成员 × 类型）
与 `word_stats`。理由：报表是高频只读操作，全表扫描会随历史线性劣化，
而预聚合让查询成本只与**时间跨度**相关。

实测 10 万条消息的分组排行查询约 20ms。

### 3. 统计口径只在一处实现

「消息数」「成员数」「活跃度」这些口径只由 `Store.insertMessage` 的事务维护。
报表、风控、面板读的是同一份数据，不会出现「报表说 100 条，统计指令说 98 条」。

### 4. 风控是「规则（纯函数）+ 引擎（窗口与计分）」

规则签名 `(消息, 配置, 历史窗口) → 判定`，纯函数带来：

- 可单测：`test/guard.test.ts` 逐个规则钉住边界行为
- 可复现：误报能拿同样的输入重放
- 可热插拔：`createRules()` 按配置组装，自定义词表规则不需要写代码

**默认不自动处罚**。群聊里一次错误禁言会让群主失去信任，而漏报只是晚一步发现。
自动动作需要显式开启 `autoActions`，且只实现「发提醒」这一可撤销的动作。

### 5. AI 分层：网关 / 检索 / 摘要互相独立

- `LlmGateway` 只管 OpenAI 兼容协议、超时、并发闸门。换厂商改配置即可
- `Retriever` 不上向量库：群聊检索多是「人名/关键词/具体事项」，词法匹配召回足够，
  用 BM25 变体 + 时效衰减重排，零额外成本
- `Summarizer` 用「分段摘要 + 归并」处理长记录，单次请求上下文可控

**AI 关闭时功能不消失**：`summarize()` 退化为统计口径摘要（谁发言最多、类型分布），
仍是有用的信息。只有「群内问答」无降级路径，明确返回 503。

### 6. 插件按声明订阅，卸载不留悬挂监听

`Plugin.subscriptions()` 返回「事件 → 处理函数」，引擎用 `插件名:事件名` 作为订阅 key。
卸载时 `offAll(插件名)` 一次摘净。长跑进程里这类泄漏会让内存只增不减且极难定位。

插件依赖用 Kahn 拓扑排序，有环或依赖缺失直接启动失败。

### 7. 事件派发同步且互相隔离

`EventBus.emit` 同步调用各订阅者，单个订阅者抛错被捕获并转发到 `engine.error`，
不影响其他订阅者 —— 一个统计插件写库失败不该让风控插件漏掉这条消息。

同步派发保证了同一消息在所有订阅者眼中顺序一致。慢操作（LLM 调用、HTTP 请求）
由插件自己 `void (async () => ...)()` 排队，不阻塞链路。

### 8. 中文分词用 2-gram 而非词典

不引 jieba/segment：群聊统计要的是「高频词与话题倾向」，不是精确分词。
词典分词会带来几 MB 词典、原生依赖，且对梗、缩写、新词反而不如字级 n-gram 稳。
CJK 切 2-gram + 拉丁按词，零依赖且口径稳定。

## 数据模型

```
conversations  会话档案（累计消息数是历史口径，不随留存裁剪回退）
members        成员台账（会话 × 成员）
messages       原始消息（可裁剪）
activity_buckets  预聚合：会话 × 时间桶 × 成员 × 类型
word_stats     词频：会话 × 词（按「出现该词的消息数」计数）
events         风控与 AI 结论留痕
kv             群知识与内部状态
```

索引：`idx_messages_conv_ts`、`idx_messages_conv_sender_ts`、`idx_activity_conv_bucket`、
`idx_word_conv_count`、`idx_events_conv_ts`。

## 已知边界

- **单机限定**：SQLite + 进程内窗口，未做多实例共享。要横向扩展需把 `Store` 与
  `GuardEngine` 的窗口换成 Redis/Postgres，接口已抽出。
- **群知识抽取是启发式的**：用「消息够长 + 含规则类词 + 非疑问句」筛候选，
  不逐条调 LLM（成本与稳定性都不划算）。候选与正式条目分表存，人工确认后才进问答语料。
- **语义审核未默认开启**：`guard.useAi` 需要 AI 可用；当前内置规则是词法+行为特征，
  覆盖不了纯语义的阴阳怪气与隐喻导流，需要时可扩展。
